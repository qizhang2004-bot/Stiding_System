# 井下排班系统（Stiding_System）

一个基于 **Django + OR-Tools CP-SAT** 的排班系统，组织结构为：

```
队组（登录/权限单位）：综掘五队、综掘二队
  └── 班组：检修班、运输班、生产一班、生产二班、生产三班（每队组各有自己的班组）
        └── 人员
班次：早班、中班、晚班
```

每个班组存储自己的排班约束，一键生成周期排班表。支持**班次展示**（日历显示每天每班次
人数、按班组分层，点击逐层下钻到个人并联动改班）、**个人日历**（上班日打「下井·班次」
标签，点击即可在 早班/中班/晚班/休息 之间修改；已上班数按日期自动累计，周期从每月 25 号起算）。

- 算法模型：`project/app/scheduler/scheduling.py`（**单一文件**，不依赖 Django，可独立运行）
- 界面逻辑：`project/app/scheduler/views.py` + `templates/scheduler/`

## 一、项目介绍

| 项 | 说明 |
| --- | --- |
| 技术栈 | Python 3.10+、Django 6.0、OR-Tools（CP-SAT 求解器）、SQLite（可换 MySQL） |
| 界面风格 | 渐变背景 + 半透明白框（毛玻璃）+ 左侧统一导航栏 |
| 排班周期 | 每月 **25 号开始算下一个月**：某月 M 的周期 = 上月 25 号 ~ 本月 24 号 |
| 队组 / 班组 | 队组：综掘五队、综掘二队；班组：检修班 / 运输班 / 生产一班 / 生产二班 / 生产三班（每个队组各有自己的班组，由超级管理员在后台管理） |
| 人员导入 | `班组-姓名-岗位1,岗位2-已上班数-应上班数-默认班次`（队组账号导入的人员自动归入本队组下的对应班组，默认归检修班；默认班次可不写，默认早班） |
| 已上班数 | 导入初始值 + 该班组最近排班中「日期 ≤ 今天」的上班天数，**按日期每天自动累加** |

## 二、页面介绍

### 1. 首页（`/`）
使用流程引导 + 系统内置休息规则说明 + 当前数据统计（人员/班组/排班记录数）+ 最近排班入口。

### 2. 班组管理（`/teams/`）
标题显示当前队组（如「综掘五队 · 班组管理」），顶部是**该队组下的班组标签**，点击哪个班组就显示哪个班组的存储约束与人员（超级管理员可看所有队组的班组，标签显示「队组·班组」）：
- **1.1 该班应上人数**（每天下井总人数）
- **1.2 固定岗位应上人数**：岗位从该班人员的岗位中去重选择（条件：至少 ≥ / 至多 ≤ / 等于 =）
- **1.3 连休范围**：休息必须连休，天数在 ≥ ~ ≤ 之间（默认 2~4 天，最大值默认 ≈（周期天数−最少班数）/3）
- **1.4 每人应上最少班数 + 豁免人员弹窗**（勾选豁免，不需要达到最少班数）
- **容量预估卡片**：按当前约束算出最多能满班几人、需要豁免几人（如 25 人每天 13 人 → 最多 20~21 人满 18 班，需豁免 4~5 人）
- 【保存约束】【生成排班】按钮（生成自动使用存储的约束）
- **导入人员**区（粘贴/上传）
- **该班的人**：姓名/岗位/默认班次/已上班数（自动）/应上班数/操作；**按岗位多选筛选**（含「所有」）

### 3. 班次展示（`/board/`）
日历显示**当月每一天每个班次上班人数**，每个班次用框隔开、按班组分层（如 `早班：13人 → 检修班 13人`）。
顶部可切换月份（默认 25 号起算的下一月）。点击班次框 → **班次详情页**：
列出该班次各班组上班人员的 姓名/岗位/已上班数/应上班数，点人名跳转个人日历，**修改全表联动**。

### 4. 个人日历（`/persons/<id>/`）
- 顶部**月份选择器**（◀上月 / 年月 / 下月▶ + 跳转，默认显示 25 号起算的下一月）
- 日历上上班日打 **「下井·班次」标签**（带 ● 的是今天），**每个格子都有下拉**可改：早班/中班/晚班/休息，改完自动保存并联动班次展示与结果页
- 顶部统计：班组、默认班次、已上班数（按日期自动）、应上班数/还需

### 5. 排班记录（`/schedule/list/`）
所有排班记录（每班组每月只保留最新一份）：班组/月份/每天下井人数/岗位条件/最少班数/豁免/状态/时间，点击查看结果。

### 6. 排班结果（`/schedule/<id>/`）
- 统计卡片：求解状态 / 达标人数 / 人均班数 / 单休·连休违规数
- **排班不足警告**：有人未达到应上班数时，先给出容量数学（最多几人能满班、需豁免几人），再列出短名单（谁需 X 班只排了 Y 班），提醒去班组管理设豁免
- 周期每日每班名单（带日期）+ 每人「已上/应上/本次/达标」统计

## 三、算法模型描述（`project/app/scheduler/scheduling.py`）

### 建模方式
把「某人某天是否上某班」建模成 **0/1 变量**：
- `x[人, 天, 班次]`：是否上该班次（早/中/晚）
- `y[人, 天]`：当天是否上班；`r[人, 天]`：当天是否休息（= 1 − y）

交给 OR-Tools CP-SAT（`from ortools.sat.python import cp_model`）求解：
满足所有硬性约束的前提下，尽量优化软性目标。

### 硬性约束（必须全部满足）
1. **每天下井人数**：`每天所有班次总人数 == 该班应上人数`（也兼容每班精确人数）
2. **一人一天最多一个班**
3. **岗位人数条件**：每天该岗位上班人数满足 至少 ≥ / 至多 ≤ / 等于 =
4. **连续工作窗口**：任意连续 10 天内最多上 6 班（每 10 天至少休 4 天 → 每人周期内最多 18~19 班）
5. **连休规则**：连续休息天数 ∈ [最少, 最多]（默认 2~4）；不允许单休（含月初/月末边界）、不允许连休超上限
   - 由此推出**每人最少也要上 6~7 班**（休息排不满周期天数）

### 软性目标（尽量满足）
6. **最大化达标人数**：`reached[人] = (班数 ≥ 该人目标)`，目标是「应上班数 − 已上班数」（没填用班组最少班数）
7. **尽量接近目标**：每人偏离目标班数有惩罚
8. **默认班次偏好**：尽量排默认班次（早/中/晚）
9. **豁免人员**：不参与达标、不施加接近目标的压力

### 两阶段求解策略
- **阶段一**：最大化达标人数（模型不带偏离变量，更快）
- **阶段二**：固定达标人数 → 最小化偏离 + 默认班次偏好（用阶段一解作 hint 起步，保证快速找到可行解）
- 有连休规则时给每人一个「上6休4」错峰初始提示，帮助搜索收敛

### 可行性预检与容量预估
- `validate_config`：求解前检查总班次是否超出容量、岗位条件是否超员、参数是否合法，给出人话诊断
- `capacity_analysis`（纯函数）：按 人数、每天应上人数、周期天数、连休上限、目标班数 计算：
  - `min_work`（连休规则限定的每人最少班数）、`max_work`（10 天窗口上限）
  - `max_fillable`（最多能满班几人）、`needed_exempt`（需要豁免几人）
  - 例：25 人、每天 13 人、31 天、目标 18 → 总 403 班 → 最多 21 人能满 18 班 → 需豁免 4 人

## 五、常见问题

- **求解提示无解？** 通常是每天应上人数太高或岗位条件过严，页面会给出诊断信息（如"总班次需求超出全员容量"）。
- **豁免后还有人排不满？** 多半是**岗位条件用了「等于 =」**。例如「电工 每天等于 2 人」：5 名电工 × 18 班 = 90 班，
  但每天恰好 2 人 × 31 天只有 62 个电工班，电工注定排不满。解决：把岗位条件改成「**至少 ≥**」，
  或把该岗位人员设为豁免，或降低该岗位人员应上班数。系统会自动判断：容量足够时把达标设成硬约束（豁免后全达标）；
  岗位条件导致不可行时回退为「最大化达标人数」，并在结果页列出排不满的人与原因。
- **有人排不满？** 容量有限时必然有人排不满，结果页会给出「最多能满几人/需要豁免几人」并列出名单，
  去班组管理把这些人员设为豁免后重新生成即可。
- **已上班数怎么算？** 导入初始值 + 本班组最近排班中「日期 ≤ 今天」的上班天数，每天自动更新；
  周期按每月 25 号起算（可在 `views.py` 的 `PERIOD_START_DAY` 修改）。
- **休息规则能改吗？** 连休范围每个班组可单独设置；10 天 ≤6 班窗口在 `views.py` 的 `DEFAULT_WORK_WINDOW`。
