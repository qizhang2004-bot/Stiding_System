# 排班规则与算法说明（规划）

## 已实现

### 第一阶段：人多人少判断与班数分配

- 模块：`apps/scheduler/engine/allocator.py`（纯计算）、`apps/scheduler/planning.py`（Django 适配层）。
- 变量来源：D=周期天数（每月25日至次月24日，`selectors.period_range`，跨月/跨年）、
  R=`daily_worker_count`、M=`required_shifts`（每人目标班数，默认 18）、
  N=班组在职职工数、豁免=`exempt_employee_ids`、岗位资格=`parse_positions(position)`。
- 判断（以公式为准）：可排开最大人数 = D×R÷M；>N → 人多模式（算法一），≤N → 人少模式（算法二）。
  - 算法一（人多/名额有剩余）：普通人员全部达到 M；剩余名额优先由豁免人员承担（组内班数差 ≤1），
    无法承担部分由普通人员平均分担（班数差 ≤1）。
  - 算法二（人少/名额紧张，修复版）：K = min(N, floor(D×R÷M)) 为理论可保证 M 班的普通人员数；
    **普通人员目标 = M（硬性下限，绝不悄悄降低）**；剩余需求 D×R − 普通人数×M 由豁免人员公平分配
    （组内班数差 ≤1）；普通人员数超过 K 且豁免不足时明确报告不可行（如“需要至少豁免 X 人”）。
    理论豁免 E = N − K、豁免剩余目标 R' = D − K×M 作为预检信息输出。
  - 理论不可行（有效职工为 0、R>N、豁免人数不足等）返回不可行并说明原因。
- `employee.min_required_shifts`（矿上最低出勤班数）只用于展示/统计/预警，**不参与**算法。

### 第二阶段：每日上班人数硬约束

- 模块：`apps/scheduler/engine/daily_solver.py`（CP-SAT 每日求解）。
- 硬约束：每天实际安排人数**严格等于** `daily_worker_count`（不多不少）；
  每人每天至多一班（0/1 单变量天然满足）；人员仅来自本班组（适配层组装）。
- 目标：最小化每人实际班数与第一阶段分配目标的绝对偏差之和；
  第一阶段目标为“目标值/基线”，不直接当作最终排班结果。
- 不可行（R>N、空班组等）时明确报告原因，**绝不修改 R 制造可行解**；
  求解后对逐日人数做防御性复核。

### 第三阶段：特殊岗位人数约束

- 模块：`apps/scheduler/engine/position_solver.py`（每日人数 + 岗位人数联合求解）。
- 岗位资格：复用 `parse_positions(Employee.position)`（、，, 分隔符，去空格/空项/去重）；
  岗位人数配置读取 `ShiftConfig.position_requirements`（{岗位: 要求人数}，精确人数）。
- 硬约束：每天总人数 == R；每天每岗位实际人数 == 配置人数（恰好，非最低）；
  职工只能承担具备资格的岗位（未获资格对不创建变量）；每人每天最多一个实际岗位；
  岗位安排必须落在上班日期（岗位人员计入当日总人数，不重复计数）。
- 目标：班数目标偏差最小化（同第二阶段）；岗位约束迫使目标无法达成时，
  如实返回实际班数、目标班数与偏差（不放松任何硬约束）。
- 不可行原因：岗位要求超过具备资格人数、岗位要求合计超过每日人数、
  多岗位人员竞争冲突等，均由 `diagnose_position_infeasibility` 明确报告。
- 独立校验：`validate_position_solution` 逐条复核（每日人数、岗位人数、一人一岗、
  资格、人员范围、偏差统计），校验失败不返回成功结果。

### 第四阶段：休息规则（含连续休息上下限硬约束，2026 修复）

- **硬约束（不可静默放宽）**：
  - R1 禁止孤立工作日（休—上—休）；R2 禁止单日休息（上—休—上）；
  - R4 **连续休息上限**：任意 max_consecutive_rest_days+1 个连续日期至少 1 天上班
    （含相邻周期边界已知时的拼接判定）；超过上限即无解并明确报因；
  - R5 **连续休息下限**：禁止长度小于 min_consecutive_rest_days 的休息段（min=2 等价于 R2）；
  - **普通人员最低班数硬下限**：非豁免职工实际班数 ≥ required_shifts；容量不足时
    返回明确冲突原因（"普通人员最低班数合计 X 班 + 豁免受休息上限至少需 Y 班 > 周期总需求 Z 班"）。
- **边界未知不判定**：缺少相邻周期真实数据时，与未知边界相接的首/尾休息段不参与
  判定（模型与独立校验器一致，不虚构边界状态）。
- 软目标：10 天滑动窗口尽量含连续 2~3 天休息（未达成不影响可行性）。

### 原始阶段说明：休息规则

- 模块：`apps/scheduler/engine/rest_solver.py`；复用 `position_solver._build_base_model`
  共享前三阶段变量与约束（不另起引擎、约束不重复定义）。
- 硬性休息规则（周期内部日期完整应用）：
  - 禁止孤立工作日（休—上—休）：`x[d] <= x[d-1] + x[d+1]`
  - 禁止单日休息（上—休—上）：`x[d-1] + x[d+1] <= 1 + x[d]`
- 周期首尾边界：读取相邻周期真实排班记录（`ScheduleRecord`，start−1 / end+1）；
  无数据时不虚构边界状态，结果 `boundary_note` 说明边界限制。
- 软性优化（10天滑动窗口）：每个窗口尽量含连续2至3天休息
  （`has2/has3` 布尔变量），未达成不算无解，仅报告"休息优化未完全满足"。
- 目标优先级（词典序优化 `_solve_lexicographic`，逐级求解并固定上一级最优值，
  不用任意权重）：硬约束 → 硬性休息规则 → 班数目标偏差最小 → 2天窗口数最大 → 3天窗口数最大。
- 不可行诊断 `diagnose_rest_infeasibility`：区分基础约束不可行（每日/岗位）
  与"基础可行但休息规则无解"，并如实说明无法精确定位冲突的诊断能力边界。
- 独立校验 `validate_rest_solution`：前三阶段检查 + 两条休息规则（含边界数据）
  + 休息质量指标统计正确性；软目标未满足不判无效。

### 第五阶段：统一综合求解入口

- 模块：`apps/scheduler/planning.py` 的 `solve_shift_schedule()`（返回 `ShiftScheduleResult`）。
- 调用链：`period_range` → 有效职工/岗位资格（`parse_positions`）→ `plan_shift_targets`
  （人多人少 + 班数目标）→ `build_rest_problem`（边界数据）→ `solve_rest_assignment`
  （同一 CP-SAT 模型：每日人数 + 岗位 + 休息全部硬约束共同生效，词典序优化）
  → `validate_rest_solution` 独立校验 → 汇总统一结果。
- 状态：`feasible` / `infeasible` / `unknown`（求解超时未确定，既不算不可行也不算成功）
  / `invalid`（独立校验失败，不得返回成功）。
- 词典序：班数偏差最小 → 含连续2天休息窗口数最大 → 含连续3天休息窗口数最大；
  首级目标已最优但软目标超时未证明最优时，返回当前可行解并在消息中注明。
- 统一结果字段：status/mode/周期/每日人数/目标与实际班数/总偏差/岗位逐日汇总
  （要求、资格、逐日人数、是否逐日精确匹配）/休息质量/边界说明/校验错误/诊断信息，
  并保留底层 allocation 与 solution 供草稿生成使用。
- 诊断分类：每日人数不可行、岗位不可行、基础可行但休息规则无解、超时未确定、
  可行但班数目标偏差、可行但休息软目标未满足、独立校验失败（如实说明能力边界）。

### 第六阶段：排班草稿生成与确认保存

- 模块：`apps/scheduler/drafting.py`；模型 `ScheduleBatch`（scheduler 0002 迁移，仅新增表）。
- 草稿只存 `schedule_batch`（批次元数据 + payload 明细 JSON + 配置/职工快照 + 求解摘要），
  不写入 `ScheduleRecord`；只有 feasible 且独立校验通过的结果才能生成草稿。
- 确认（单事务）：行锁（select_for_update）→ 权限 → 状态 → 配置/职工/岗位资格/周期复核
  → 正式排班冲突检查 → 重新独立校验 → 展开明细写入 ScheduleRecord（status=confirmed，
  沿用草稿批次号，含休息行）→ 更新批次状态/确认人/确认时间 → 操作日志；异常整体回滚。
- 班次口径（已确认调整）：人员池 = 班组在职职工；`ScheduleRecord.clean()` 放宽为
  “职工必须属于本班组”，允许同班组内跨班次职工写入，跨班组仍拒绝。
- 草稿绝不进入正式排班、统计与跨周期边界查询（这些查询只读 schedule_record）。

### 第六阶段补充：正式排班冲突与作废替换（2026 修复）

- 冲突校验范围：同**班组**、同排班周期、状态为 confirmed/published 的记录，
  与草稿 payload 的 (职工, 日期) 重叠即冲突（本批次自身记录除外）。
- 默认阻止确认并给出冲突明细（总数、前 20 条含职工/日期/班组/记录ID/批次/班次）。
- 显式「作废旧批次并确认」：在单事务内把冲突来源批次及其记录标记为
  `superseded`（**保留全部历史记录，不删除**），再写入新版本；已作废记录
  不再计入冲突、边界数据与出勤统计。同一批次的重复确认仍被状态检查阻止。

## 算法输入（来自 shift_config / employee）

| 配置 | 含义 | 算法用途 |
| --- | --- | --- |
| daily_worker_count | 该班次每天需要安排的上班人数 | 每日硬需求（恰好等于） |
| min_consecutive_rest_days | 连续休息最少天数 | 连休下限约束 |
| max_consecutive_rest_days | 连续休息最多天数 | 连休上限约束 |
| required_shifts | 每人目标班数（默认 18） | 班数分配目标 |
| position_requirements | 各岗位要求人数 {岗位: 人数} | 岗位硬需求（恰好等于） |
| exempt_employee_ids | 豁免人员ID列表 | 人多模式剩余名额优先承担 |
| employee.position | 岗位资格（分隔符解析） | 岗位资格判定 |

## 排班周期

每月 25 日至次月 24 日；`employee.worked_shifts` 仅统计当前周期，不跨周期累计。

## 排班批次

每次生成一版排班结果使用新的 `schedule_batch_id`；
重新生成或调整后需要保留历史版本时，不覆盖其他批次数据
（唯一约束：批次 + 职工 + 日期）。休息日同样保存记录（shift_type=rest）。

## 引擎

`apps/scheduler/engine/` 含 OR-Tools CP-SAT 基线（决策变量 x[e,d,s]、硬约束 H1-H4、
无解诊断）与第一阶段分配模块（allocator.py）；后续阶段在既有求解器上按上述顺序
重建成约束与目标，不另起引擎。
